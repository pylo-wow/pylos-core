# The frame: services, versions, modules, saved data

The rules every Pylos addon follows. Pylos Core (`PylosCore`) holds the frame; it has no game data.
What an addon may rely on from the core is listed in `README.md`; this file explains how the family fits together.

## 1. Principles

1. **Facts go to PylosData, weighing to PylosData\Engine, presentation to a module, frame to PylosCore, look to PylosUI.**
2. **No addon reaches into the globals or the inside of another.** Everything runs through **services**
   (named tables with a version) that one asks the core for.
   The one exception is for players' macros and key bindings: `PylosSpotlight`, `PylosSpotlight_Show`
   and `PylosSpotlight_Toggle` stay globals.
3. **Versions.** Every service has `major.minor`.
   - minor +1: something was added (a new function, a new optional field). Old users keep working.
   - major +1: something that exists changes its meaning or goes away. The provider offers the old
     major version **beside** the new one until all its own modules have moved over (at least one
     release), with a compatibility table.
   - The addon version in the TOC (`## Version: x.y.z`, SemVer) is separate: it counts releases of the
     addon, not its interfaces.
4. **A module says what it needs** (a service and a minimum version). If something is missing or too
   old, only that module switches itself off (`ns.off`), with a clear message in the chat and on the
   settings page "Pylos". No Lua error.
5. **Saved data has a shape number** (`_schema`) and a chain of migrations. Unknown keys are never
   deleted; only a migration removes something.
6. **Extensions go through registrations** (`ns.RegisterSource`, `RegisterFilter`, `ns.RegisterReason`,
   `ns.RegisterPush`, `D.AddField`, `D.Need`), not through reaching into foreign code.
7. **Internal services** for closely coupled modules of one family are called `<name>.internal`
   (e.g. `engine.internal`). They may change freely in any major version; every incompatible change
   raises their major number so the version check works.

## 2. The services

| Service | Version | Provider | Content | Used by |
|---|---|---|---|---|
| `core` | 1.0 | PylosCore | the global `PylosCore`: `Module` (stable); `Provide`, `Get`, `NewLocale`, `Saved` (provisional) | all |
| `widgets` | 1.0 | PylosUI | the shared building blocks of the windows | Spotlight, Recommendations, Upgrades |
| `data` | 1.1 | PylosData | the `PylosData` table (the public list at the head of `PylosData\Core\Core.lua`) | all that use Data |
| `engine` | 1.0 | PylosData | the public API of the recommendation engine | Spotlight, Recommendations, Upgrades |
| `engine.internal` | 1.0 | PylosData | the whole engine table (reasons, memory, learning, reach, service, ItemValue, ...) | Recommendations, Upgrades |
| `spotlight` | 1.0 | PylosSpotlight | `{ API, Show, BackgroundAlpha }` (as the global `PylosSpotlight`) | Recommendations |
| `gatherinfo` | 1.0 | PylosGatherInfo | `{ AddLine, Wanted }` | Spotlight |

`Provide(name, version, impl, by, names)`: `names` is the list of public fields. At `PLAYER_LOGIN` the
core checks that every named field exists (otherwise the provider has a problem). For `*.internal`
services no list of names is given.

## 3. A module: the fixed layout

Every addon of the family (except PylosCore) has as its **first file** `Init.lua`:

```lua
local addonName, ns = ...
-- Announces the addon to Pylos Core: its texts (ns.L), its options page from ns.options, and
-- whether what it needs is there (ns.off: then every file of it returns at once).
if not PylosCore.Module(addonName, ns, { requires = { core = "1.0", data = "1.0", widgets = "1.0" } }) then return end
ns.data = PylosCore.Get("data", "1.0")
ns.widgets = PylosCore.Get("widgets", "1.0")
```

(Each addon only the services it needs. Small addons: only `core`.)

**Every other Lua file** of the addon (as listed in the TOC; except generated data files with
`-- Generated by` in their head) has, right after its `local ..., ns = ...` line:

```lua
if ns.off then return end
```

In PylosData the namespace is called `D`: `if D.off then return end`.
Files read services from `ns` (`local D = ns.data`, `local W = ns.widgets`), never from globals.

## 4. Saved data

`PylosCore.Saved(globalName, spec)`:
- `spec.defaults`: key -> value, put in where the key is `nil` (tables are copied).
- `spec.version` (a number, default 1) and `spec.migrations[n] = function(db)` (n-1 to n).
- If the table was missing: `_schema = version`, no migrations. A table without `_schema`: shape 0.
- Newer data (`_schema` > version, e.g. after a downgrade): left as it is, `_schema` is not lowered.
- Unknown keys stay.

The options framework uses `Saved` (with an optional `ns.options.schema = { version, migrations }`) and
never deletes keys that are not in `defaults`.

Taking over data between addons: the receiver copies it on first load (a migration of its own), the
sender removes it only in a later schema version. So nothing is lost, whatever order the addons load in.

## 5. Settings

- The core makes a category **"Pylos"** (vertical layout). Each module gets a subcategory below it
  (`Settings.RegisterVerticalLayoutSubcategory`), its `page` entries below that
  (`RegisterCanvasLayoutSubcategory`). "Pylos" is registered once at `PLAYER_LOGIN` (after every
  `ADDON_LOADED`).
- The page "Pylos" shows an introductory sentence and one line per module: title, version, state
  ("OK" in green, otherwise the reason).
- Minimap buttons stay per module (a right-click opens the module's page).

## 6. Messages

At `PLAYER_LOGIN` (after the contract check), one chat line per module that is off or has a problem:
- Service too old: `Pylos Spotlight is off: it needs Pylos Data (data 1.4), you have 1.2. Update Pylos Data.`
- Service missing: `Pylos Spotlight is off: it needs data 1.4, which is missing.`
- Contract broken (a developer's mistake): `Pylos Data: data 1.0 lacks Gathering.`

The texts are English only for now; translations come later.
